NeuralChain AI Model Marketplace

Current hybrid architecture, data flow, implemented behavior, and prototype boundaries

This HTML file is the current architecture source. The bundled PDF is a historical export and may not include these updates.

In one sentence: NeuralChain is a hybrid AI-model marketplace. Smart contracts record model listings, creator addresses, payments, purchase events, and license access. Model files are stored on IPFS. The MongoDB and Express backend provides user accounts, searchable metadata, moderation, and download authorization.

1. System Map

Browser (React + Vite + ethers.js + MetaMask) | REST/JSON | signed blockchain transactions v v Express API (Node.js) ---- RPC ----> EVM chain / Hardhat / Sepolia | \ | ModelMarketplace | \ | ModelNFT + NeuralToken | v v MongoDB Atlas Pinata API ----> IPFS gateway / content-addressed model file (catalog, users, (optional) (CID / modelHash in the listing) purchases, reviews)

The EVM contract is authoritative for listing references, purchase events, payment settlement, and license access. The backend handles accounts, metadata, moderation, and joins contract data with searchable MongoDB records. IPFS stores model files, while MongoDB is an off-chain application index and history store.

2. What Connects to What

3. Upload and Listing Flow

  1. The authenticated creator selects a model in React. The browser uploads it to POST /api/ipfs/upload; it does not receive a decryption key.
  2. Multer keeps the upload in memory and limits it to 100 MB. Static checks run and SHA-256 is calculated over the original bytes. Architecture fingerprint, metadata similarity, and version lineage can flag duplicates for moderation.
  3. For a paid model, Express encrypts the file with AES-256-GCM and wraps the random content key using the required MODEL_ENCRYPTION_SECRET. The encrypted file is sent to Pinata or saved by the local demo fallback.
  4. The creator signs the compact listing transaction: encrypted CID, original-file SHA-256, decryption-key hash, price, and optional parent listing ID. No plaintext key or model weights are stored on-chain.
  5. Express joins the authoritative listing read from the contract with searchable MongoDB metadata. JSON persistence and local deterministic storage are development/demo fallbacks.
  6. An admin can approve the listing. Public marketplace queries expose only verified or legacy records.

4. Contracts and Transaction Workings

ModelMarketplace.sol

  • Stores model ID, creator address, encrypted-file CID, original-file SHA-256, key hash, price, optional parent listing ID, active state, and creation time.
  • Accepts ETH or NEURAL payments.
  • Uses personal, commercial, and enterprise multipliers of 1x, 3x, and 10x.
  • Primary-sale split: 10% platform / 90% creator without a parent; with a parent, 10% platform / 10% parent creator / 80% listing creator.
  • Emits events used by the backend for receipt verification.

ModelNFT.sol

  • ERC-1155 license token minted after purchase.
  • Ownership is transferred to the marketplace during deployment, allowing the marketplace to mint.
  • Transfers are blocked except minting and burning. No secondary resale market or ERC-2981 resale royalty is implemented.

NeuralToken.sol

  • ERC-20 token named NEURAL with permit and vote support.
  • Used for purchases and governance-related voting power.
  • The deployment script deploys the token contract. It does not fund a fake frontend or buyer wallet.

Receipt verification

  • Backend loads the marketplace ABI and queries the transaction plus receipt through the RPC.
  • It parses ModelPurchased or NeuralPurchase, then records model ID, tier, amount, and block number.
  • Production must use a live RPC and real contract address; local fallback is explicitly demo behavior.

5. Purchase and Access Flow

Buyer selects tier -> MetaMask signs transaction -> contract checks listing, price, tier, and payment -> primary-sale split -> non-transferable ERC-1155 license minted -> backend verifies receipt -> wallet-signed access request -> contract access check -> backend releases wrapped-key decryption key

ETH purchases use the transaction value. NEURAL purchases require an ERC-20 allowance and use transferFrom. Backend purchase records are application history; the contract remains authoritative for listing and access. The inference/API prototype does not execute uploaded model files.

6. MongoDB, Authentication, and Supporting Services

  • MongoDB Atlas: stores records that are awkward or expensive to query on-chain: profiles, descriptions, tags, benchmarks, moderation notes, reviews, downloads, API keys, and purchase history. Mongoose adds schemas and indexes.
  • JWT authentication: Express issues tokens for registered users; Axios attaches the token to API calls. A creator wallet is linked to the account after a wallet signature; wallet signatures and contract access checks are used for encrypted-key release.
  • Moderation: static file verification runs before upload completion, while admin review controls marketplace visibility. The verifier does not execute uploaded model code or measure real accuracy.
  • API prototype: API-key and completion endpoints can return sample responses. They do not execute uploaded model files.
  • Local deployment: Hardhat compiles/deploys contracts; the deployment script synchronizes ABI and addresses to frontend and backend. Cloud operations and production readiness are outside this implementation.

7. On-chain and Off-chain Responsibilities

Concern On-chain component Off-chain component
Ownership and payment Compact model references, creator addresses, payment settlement, purchase events, and license access. Accounts, searchable listing metadata, moderation, and purchase-history joins.
Artifact integrity The CID addresses the encrypted paid file; SHA-256 is used for exact original-file integrity checks. MongoDB stores searchable verification and model metadata.
Portability Wallet accounts, events, and access state can be read from the configured EVM network. Express authentication and MongoDB account/profile services coordinate the application.
Creator economics Primary-sale payment allocation and license minting are contract transactions. Metadata, moderation, and proposal/vote records are application data.
Availability Contract state is on the selected EVM network; IPFS content is available only while pinned and retrievable. API, database, moderation, and key-envelope storage depend on configured services.
Trade-offs Gas fees, confirmation time, wallet UX, irreversible mistakes, RPC dependence, and smart-contract risk. Faster UX, easier refunds, simpler recovery, but greater platform custody and trust.

8. Implemented, Prototype, and Future Scope

Implemented: compact contract listings, primary-sale payment settlement, non-transferable ERC-1155 licenses, paid-file encryption, signed access requests, SHA-256 integrity checks, and metadata moderation.
Prototype/off-chain: MongoDB/Express marketplace services, local Hardhat demonstrations, JSON persistence and local deterministic file storage fallbacks, governance proposals/votes, and sample API responses.
Future scope: NeuralChain currently does not execute uploaded model files inside an isolated Docker sandbox. Isolated Docker inference is future scope. Managed production key storage, durable pinning, and operational hardening also require separate implementation.

Governance proposals and votes are stored off-chain; there is no on-chain DAO contract or treasury. Licenses are non-transferable; secondary resale and ERC-2981 resale royalties are not implemented.

9. Technology Summary

Languages: JavaScript (React frontend and Node.js backend), Solidity (EVM contracts), JSON (ABIs, configuration, fallback data), HTML/CSS (this guide), and shell configuration for deployment.

Core libraries and tools: React, Vite, Axios, ethers.js, Express, Mongoose, Multer, JWT, Hardhat, OpenZeppelin, MetaMask, MongoDB Atlas, Pinata, and IPFS.
